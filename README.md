### 2️⃣ 建立自己的分支（首次只做一次）

把下面命令里的 `dev-qiuyu` 换成你自己的分支名：

```bash
git checkout main
git pull origin main
git checkout -b dev-qiuyu
git push -u origin dev-qiuyu
```

执行完，你就在自己的分支上了。以后再也不用 `git checkout main` 写代码。

### 🔑 比分支更重要：文件所有权

分支只是把冲突**推迟**到合并那一刻，并不会让它消失。真正不冲突的关键是——**两个人永不修改同一个文件**。

详细的目录归属见 `04.编码/OWNERS.md`，**编码前必读**。要点：

- 属于你的目录：随便改
- 别人的目录：一眼都别碰
- `package.json`、`router/index.js`、`requirements.txt` 这三个高危文件：各有唯一负责人，要改就在群里说
- 阶段文档：一人一个 md 文件，严禁两人编辑同一个 md

## 📤 日常工作流程

### 3️⃣ 每天工作前：同步 main 的最新进度

**每天开工前先把 main 的最新进度同步到自己的分支**。推荐拆成两步写（比一句 `git pull` 更清楚发生了什么）：

```bash
# 1. 切到自己的分支（dev-qiuyu 换成你自己的）
git checkout dev-qiuyu

# 2. 只下载远程最新，不动你本地任何文件
git fetch origin

# 3. 把 main 的新进度合进你的分支
git merge origin/main

# 4. 确认状态
git status
```

> `git pull origin main` 等价于上面第 2、3 步的合成，也能用。拆开写是为了看清"下载"和"合并"是两件事。

---

### 【关键】组长合并完 main 之后，你要立刻做这一步

组长把大家的分支合并进 `main` 并推送后，**你的分支就落后于 main**。
下次动手写代码前必须补一次同步，命令和上面 3️⃣ 完全一样：

> 下面命令里的 `dev-qiuyu` 一律换成你自己的分支名：**梁霁鸣 = `dev-liang`，周彦龙 = `dev-zhou`**。

```bash
git checkout dev-qiuyu      # 换成你自己的分支
git status                  # 先确认工作区干净，有未提交的改动就先 commit
git fetch origin
git merge origin/main       # 关键一步：把 main 合进你的分支
git push origin dev-qiuyu   # 同步到你远程自己的分支
```

**为什么不能跳过：**

- `main` 里已经包含了你之前推上去的提交，所以这一步通常是**快进（fast-forward）**——不冲突、不丢东西，自己做就行
- 但如果一直不同步，你的分支基点会停在很久以前。基点越旧，将来合并跨度越大，越容易出莫名其妙的问题
- 实例：2026-09-22 合并时 `dev-liang` 的基点还停在 9/11，中间隔了概要设计 v2.0、数据库交付物、38 界面原型三轮大更新，
  组长这边只能做一次大跨度三方合并才合得进去。**按时同步的话，这种事不会发生**

**【常见误判】同步后看到一堆"删除"，以为代码没了**

跑 `git diff main..dev-qiuyu`（注意是两个点）可能看到别人的文件显示成删除——**这是假象**。
该命令比较的是两个分支的最终状态，你的分支只是还没同步到那些新文件，git 就当成了"删除"。

只看你自己的真实改动：

```bash
# 你相对公共祖先改了哪些文件
git diff --name-status $(git merge-base origin/main dev-qiuyu) dev-qiuyu

# 只查有没有真删文件（返回空 = 没有任何删除）
git diff --diff-filter=D --name-only $(git merge-base origin/main dev-qiuyu) dev-qiuyu
```

拿不准就问组长，**不要手动去"补回"这些文件**，那样反而会真的制造冲突。

---

### 4️⃣ 修改文件后：提交 & 推送

以下命令里的 `dev-qiuyu` 换成你自己的分支名。

#### ✅ 正确流程（推荐）

```bash
# 1. 查看改了什么
git status

# 2. 把所有改动加到暂存区
git add -A

# 3. 提交（写清楚改了什么）
git commit -m "feat: 完成老人端健康档案页面开发"
# 或
git commit -m "docs: 更新需求分析说明书 v1.0"
# 或
git commit -m "fix: 修复 RTM 表头错位"

# 4. 推送到【自己的分支】
git push origin dev-qiuyu
```

> ⚠️ 最后一步是推**自己的分支**，不是 `git push origin main`。

---

#### ❌ 常见错误

| 错误操作 | 问题 | 正确做法 |
|---------|------|---------|
| 直接 `git push origin main` | 污染稳定分支，极易与他人冲突 | 推自己的分支 |
| 忘记切分支就开始写 | 改动落在 main 上，很难救回来 | 动手前先 `git checkout dev-xxx` |
| `git commit` 没加 `-m` | 会打开编辑器要求写 commit 消息 | 直接 `git commit -m "消息"` |
| `git add .` 而不是 `-A` | 可能漏掉新文件 | 统一用 `git add -A` |
| 没拉直接推 | 可能因为远程有更新而失败 | 先 `git pull` 再 `git push` |
| 改了别人的文件 | 制造冲突，可能覆盖他人成果 | 查 `OWNERS.md`，要改先打招呼 |
| 写模糊的 commit 消息 | 比如 "update"、"修改" | 写清楚："feat: xxx"、"docs: xxx" |
| 用 `git pull`（不带参数）当同步 main | 只拉了自己分支，main 的更新根本没进来 | `git fetch origin` 再 `git merge origin/main` |
| 隔一两周才同步一次 main | 基点太旧，将来要大跨度合并，风险陡增 | 至少每周同步一次；组长合并后立刻同步 |
| 看到假"删除"就手动补回文件 | 反而制造真冲突 | 对 merge-base 用 `--diff-filter=D` 复查，或问组长 |

---

### 🚫 三条铁律

1. **不用 `git rebase`** —— 零基础容易整段代码丢失，我们只用 merge
2. **禁止 `git push --force`** —— 会覆盖别人的提交，出事就是灾难
3. **push 前一定先 pull** —— 养成习惯，能避开八成问题

## 📝 Commit 消息规范

我们用简单的约定式提交（Conventional Commits）：

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat: 完成 AI 咨询页面布局` |
| `docs` | 只改文档 | `docs: 更新 RTM v1.1` |
| `fix` | 修 bug | `fix: 修复 RTM 表头错位` |
| `refactor` | 重构（不改功能） | `refactor: 整理项目目录结构` |
| `chore` | 不影響业务的改动 | `chore: 删除_build 目录` |

**好消息示例：**
- ✅ `feat: 老人端健康档案新增编辑功能`
- ✅ `docs: 更新需求分析说明书 v1.0`
- ✅ `fix: 修复 RTM 中担当者列空值`

**坏消息示例：**
- ❌ `修改`
- ❌ `update`
- ❌ `test`

## ⚠️ 项目注意事项

### 📄 文档规范

1. **所有 Markdown 文件**（`.md`）是**源文件**，Word（`.docx`）由 `pandoc` 自动生成。
2. **不要直接编辑 `.docx`** —— 改对应的 `.md` 文件，重新转换即可。
3. 如果确实要改 Word（比如封面表格），改完记得同步到 `.md` 里保持内容一致。

### 📂 文件存放

- **只改自己负责部分的文件**，不要碰别人的（除非协同修改）。
- **不要改 `.gitignore`** —— 已经配置好的，误改可能导致某些文件不被追踪。
- **项目目录命名有规律**：
  - `01.` `02.` `03.` ... → 按阶段顺序编号
  - `01-文档` → **不要有**（已删除）

### 🔄 冲突解决

只要遵守文件所有权（见 `04.编码/OWNERS.md`），冲突几乎不会发生。真遇到了，按情况对号入座。

#### 情况一：pull 时提示冲突（最常见）

```bash
# 1. 看是哪些文件冲突（会显示 both modified）
git status

# 2. 打开冲突文件，找到三个标记：
#    <<<<<<< HEAD         → 你本地的内容
#    =======              → 分隔线
#    >>>>>>> origin/main  → 远程的内容
#    保留你需要的部分，把三行标记全部删掉

# 3. 标记已解决并提交
git add <冲突文件>
git commit -m "merge: 合并 main 更新，解决冲突"
```

#### 情况二：不小心改了别人的文件

```bash
# 撤销本地改动，恢复成原样
git checkout -- <文件路径>
```

#### 情况三：改乱了，想重来

```bash
# 放弃本地所有未提交的改动（危险，确认不要了再用）
git checkout .
```

> 拿不准就先问，不要盲目覆盖。Git 有历史记录，误删也能用 `git log` + `git checkout <commit-id> -- 文件路径` 找回。

## 🆘 常见问题

**Q: 我本地改了文件，但 `git status` 没看到？**  
A: 文件可能被 `.gitignore` 忽略了。检查项目根目录的 `.gitignore`。

**Q: 我想恢复某个文件到上一版？**  
A: 
```bash
git checkout HEAD -- 文件路径
```

**Q: 我误删了文件，还能找回来吗？**  
A: 可以！Git 保留所有历史：
```bash
# 查看文件历史
git log -- 文件路径

# 恢复到指定版本
git checkout <commit-id> -- 文件路径
```

**Q: 推送失败提示 "rejected"？**  
A: 说明远程有别人先推。先 `git pull` 拉最新代码，解决冲突后再推。
