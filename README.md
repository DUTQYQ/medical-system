# 康养系统实训项目

面向养老机构的 AI 健康管理与生活服务系统。系统包含老人、家属、护工、管理员四类账号，覆盖健康数据采集、风险预警、人员处理记录和院内生活服务。

截至 2026-10-16，四角色前后端及养老院业务扩展已合并到 `main`。梁霁鸣负责的个性化健康参考、历史基线波动提醒和活动推荐已于 [合并提交](https://github.com/DUTQYQ/medical-system/commit/56a07b4d38065ccc22978a17b67d90f79d6f73dd) 纳入主线。双窗口 Vite 缓存隔离修复见[后续提交](https://github.com/DUTQYQ/medical-system/commit/4ae8dab7906e345274503c4fef7c855e005e6112)。

## 系统功能

| 角色 | 主要功能 |
| --- | --- |
| 老人 | 维护个人健康档案，录入和查看指标、趋势与预警；使用健康问询、个人健康词条和易读建议；申请生活服务、报名活动、呼叫工作人员和申请设备 |
| 家属 | 仅查看已绑定且获授权老人的健康信息；查看通知、提交预警反馈、代老人申请生活服务、报名活动或申请设备 |
| 护工 | 仅管理当前负责的老人；接收服务和呼叫任务、记录处理过程、登记活动出席与设备借还；提交个体阈值调整申请 |
| 管理员 | 管理账号、档案和照护关系；配置指标与默认阈值、审核个体阈值；维护服务目录、活动建议、设备及健康知识 |

健康录入后由后端按系统默认阈值或该档案已审核的个体阈值判定风险。预警、通知、工作人员处理及记录由业务规则完成，不等待大模型。个性化活动建议只预填服务申请，仍需用户确认提交；正式排期活动单独管理。家属反馈不会代替工作人员完成预警处置。

健康问询可在首次打开时启动问询；确认后的信息可保存为个人词条，并用于生成分区清晰、便于阅读的建议。模型不可用时会明确提示，健康记录、预警和院内服务等业务仍可使用。

所有页面显示“健康建议不构成医疗诊断”。模型只负责理解、检索和解释，不生成并执行 SQL，不判断账号权限，也不直接写入业务数据。

## 技术组成

- 前端：Vue 3、Element Plus、ECharts
- 后端：Python 3.11、FastAPI、SQLAlchemy 2、Pydantic 2
- 正式数据库：MySQL 8；隔离演示使用 SQLite
- AI：后端统一配置 DeepSeek、通义千问或 GLM；向量检索使用 Chroma

后端 `.env` 存数据库连接和模型密钥，禁止将真实密钥写入前端或提交到 Git。

## 启动

首次安装、`.env` 配置和现有数据库升级步骤见[运行说明](04.编码/运行说明_康养系统_v2.0.md)。

在项目根目录打开 PowerShell：

```powershell
# 正常模式：连接本机 MySQL，打开一个角色入口
& './一键启动.ps1'

# 答辩演示：启动隔离 SQLite，并打开四个独立登录窗口
& './一键演示多窗口.ps1'

# 停止正常模式
& './一键停止.ps1'

# 仅停止多窗口演示服务
& './一键停止.ps1' -StateName demo
```

| 模式 | 前端 | 后端 | 说明 |
| --- | --- | --- | --- |
| MySQL 正常模式 | `http://127.0.0.1:5173` | `http://127.0.0.1:8000` | 使用本机 `.env` 中配置的 MySQL 和已有账号 |
| 独立演示模式 | `http://127.0.0.1:5174` | `http://127.0.0.1:8001` | 单独的 SQLite 演示数据，不写入 MySQL |

演示库初始账号如下，四个账号的初始密码均为 `Abc123456`：

| 角色 | 手机号 |
| --- | --- |
| 管理员 | `13000000001` |
| 老人 | `13000000002` |
| 家属 | `13000000003` |
| 护工 | `13000000004` |

真实 MySQL 账号由本机数据库初始化或管理员创建，不使用演示账号。健康档案、指标、问询词条和阈值等健康功能首次使用前，需要在个人中心确认授权。
