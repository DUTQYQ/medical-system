## 🌿 分支协作：三个人如何互不干扰

我们**不允许三个人都往 main 上直接提交**——那必然频繁冲突。正确做法是**每人一个长期分支**。

| 人 | 分支名 | 负责内容 |
|---|---|---|
| 丘宇乾 | `dev-qiuyu` | 后端、AI Agent、预警中心、接口层 |
| 梁霁鸣 | `dev-liang` | 老人端、家属端前端 |
| 周彦龙 | `dev-zhou` | 护工端、管理员端前端、测试 |

- `main` 是**稳定分支**，只存放里程碑版本（9/24 设计评审、10/16 代码终版），由组长合并
- 日常工作全在自己的分支上，**全程不碰 main**

### 2️⃣ 建立自己的分支（首次只做一次）

把下面命令里的 `dev-qiuyu` 换成你自己的分支名：

```bash
git checkout main
git pull origin main
git checkout -b dev-qiuyu
git push -u origin dev-qiuyu
```

执行完，你就在自己的分支上了。以后再也不用 `git checkout main` 写代码。

### 🔑 比分支更重要：文件所有权

分支只是把冲突**推迟**到合并那一刻，并不会让它消失。真正不冲突的关键是——**两个人永不修改同一个文件**。

详细的目录归属见 `04.编码/OWNERS.md`，**编码前必读**。要点：

- 属于你的目录：随便改
- 别人的目录：一眼都别碰
- `package.json`、`router/index.js`、`requirements.txt` 这三个高危文件：各有唯一负责人，要改就在群里说
- 阶段文档：一人一个 md 文件，严禁两人编辑同一个 md

## 📤 日常工作流程

### 3️⃣ 每天工作前：同步最新进度

**每天开工前先把 main 的最新进度同步到自己的分支**：

```bash
# 切到自己的分支
git checkout dev-qiuyu

# 把 main 的新进度拉进来
git pull origin main

# 确认状态
git status
```

> 如果 pull 提示冲突，看下面「冲突解决」。只要不碰别人的文件，基本不会遇到。

---

### 4️⃣ 修改文件后：提交 & 推送

以下命令里的 `dev-qiuyu` 换成你自己的分支名。

#### ✅ 正确流程（推荐）

```bash
# 1. 查看改了什么
git status

# 2. 把所有改动加到暂存区
git add -A

# 3. 提交（写清楚改了什么）
git commit -m "feat: 完成老人端健康档案页面开发"
# 或
git commit -m "docs: 更新需求分析说明书 v1.0"
# 或
git commit -m "fix: 修复 RTM 表头错位"

# 4. 推送到【自己的分支】
git push origin dev-qiuyu
```

> ⚠️ 最后一步是推**自己的分支**，不是 `git push origin main`。

---

#### ❌ 常见错误

| 错误操作 | 问题 | 正确做法 |
|---------|------|---------|
| 直接 `git push origin main` | 污染稳定分支，极易与他人冲突 | 推自己的分支 |
| 忘记切分支就开始写 | 改动落在 main 上，很难救回来 | 动手前先 `git checkout dev-xxx` |
| `git commit` 没加 `-m` | 会打开编辑器要求写 commit 消息 | 直接 `git commit -m "消息"` |
| `git add .` 而不是 `-A` | 可能漏掉新文件 | 统一用 `git add -A` |
| 没拉直接推 | 可能因为远程有更新而失败 | 先 `git pull` 再 `git push` |
| 改了别人的文件 | 制造冲突，可能覆盖他人成果 | 查 `OWNERS.md`，要改先打招呼 |
| 写模糊的 commit 消息 | 比如 "update"、"修改" | 写清楚："feat: xxx"、"docs: xxx" |

---

### 🚫 三条铁律

1. **不用 `git rebase`** —— 零基础容易整段代码丢失，我们只用 merge
2. **禁止 `git push --force`** —— 会覆盖别人的提交，出事就是灾难
3. **push 前一定先 pull** —— 养成习惯，能避开八成问题

## 📝 Commit 消息规范

我们用简单的约定式提交（Conventional Commits）：

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat: 完成 AI 咨询页面布局` |
| `docs` | 只改文档 | `docs: 更新 RTM v1.1` |
| `fix` | 修 bug | `fix: 修复 RTM 表头错位` |
| `refactor` | 重构（不改功能） | `refactor: 整理项目目录结构` |
| `chore` | 不影響业务的改动 | `chore: 删除_build 目录` |

**好消息示例：**
- ✅ `feat: 老人端健康档案新增编辑功能`
- ✅ `docs: 更新需求分析说明书 v1.0`
- ✅ `fix: 修复 RTM 中担当者列空值`

**坏消息示例：**
- ❌ `修改`
- ❌ `update`
- ❌ `test`

## ⚠️ 项目注意事项

### 📄 文档规范

1. **所有 Markdown 文件**（`.md`）是**源文件**，Word（`.docx`）由 `pandoc` 自动生成。
2. **不要直接编辑 `.docx`** —— 改对应的 `.md` 文件，重新转换即可。
3. 如果确实要改 Word（比如封面表格），改完记得同步到 `.md` 里保持内容一致。

### 📂 文件存放

- **只改自己负责部分的文件**，不要碰别人的（除非协同修改）。
- **不要改 `.gitignore`** —— 已经配置好的，误改可能导致某些文件不被追踪。
- **项目目录命名有规律**：
  - `01.` `02.` `03.` ... → 按阶段顺序编号
  - `01-文档` → **不要有**（已删除）

### 🔄 冲突解决

只要遵守文件所有权（见 `04.编码/OWNERS.md`），冲突几乎不会发生。真遇到了，按情况对号入座。

#### 情况一：pull 时提示冲突（最常见）

```bash
# 1. 看是哪些文件冲突（会显示 both modified）
git status

# 2. 打开冲突文件，找到三个标记：
#    <<<<<<< HEAD         → 你本地的内容
#    =======              → 分隔线
#    >>>>>>> origin/main  → 远程的内容
#    保留你需要的部分，把三行标记全部删掉

# 3. 标记已解决并提交
git add <冲突文件>
git commit -m "merge: 合并 main 更新，解决冲突"
```

#### 情况二：不小心改了别人的文件

```bash
# 撤销本地改动，恢复成原样
git checkout -- <文件路径>
```

#### 情况三：改乱了，想重来

```bash
# 放弃本地所有未提交的改动（危险，确认不要了再用）
git checkout .
```

> 拿不准就先问，不要盲目覆盖。Git 有历史记录，误删也能用 `git log` + `git checkout <commit-id> -- 文件路径` 找回。

- 重要修改后，建议推送到远程。

## 🆘 常见问题

**Q: 我本地改了文件，但 `git status` 没看到？**  
A: 文件可能被 `.gitignore` 忽略了。检查项目根目录的 `.gitignore`。

**Q: 我想恢复某个文件到上一版？**  
A: 
```bash
git checkout HEAD -- 文件路径
```

**Q: 我误删了文件，还能找回来吗？**  
A: 可以！Git 保留所有历史：
```bash
# 查看文件历史
git log -- 文件路径

# 恢复到指定版本
git checkout <commit-id> -- 文件路径
```

**Q: 推送失败提示 "rejected"？**  
A: 说明远程有别人先推。先 `git pull` 拉最新代码，解决冲突后再推。
