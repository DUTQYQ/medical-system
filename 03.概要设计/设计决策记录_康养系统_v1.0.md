## 0. 本文件的定位

需求说明书回答"做什么"，界面清单回答"长什么样"，API 契约回答"前后端怎么对话"。
本文件回答的是**这三份文档都没写、但写代码时一定会遇到的那部分**：

- 某个操作谁有权做
- 某个流程缺了一步会出什么事
- 某个外部依赖（AI 模型）挂了以后系统还要不要继续跑

每节格式为：**问题 → 证据 → 决策 → 落地动作 → 受影响文件**。决策一旦写入，后续文档与代码按此执行；若要推翻，在本文件新增一条更高版本的决策，不静默修改旧条目。

## 1. 六个设计缺口的裁决

### D-01　注册权限边界：公开注册不得产生高权限账号

**问题**
公开注册接口允许请求体传入 `ADMIN`、`CARE`，未说明限制。照此实现，任何人在注册页构造请求即可自行成为管理员或护工，可查看全部老人档案与预警规则。

**证据**
`03.概要设计/API接口契约` 评审时版本（v0.1）第 2.1 节：`权限：公开`，`role` 取值 `ELDER / FAMILY / CARE / ADMIN`。

**决策**

1. **公开注册只允许 `ELDER` 和 `FAMILY` 两种角色**。`CARE`、`ADMIN` 不在白名单内。
2. 请求体携带非白名单角色时，后端**不做静默降级**（不能悄悄改成 ELDER，这会让用户以为注册成功），而是返回业务错误码 `4003 该角色不允许自助注册`。
3. 请求体不传 `role` 时，默认 `ELDER`。
4. **护工与管理员账号只能由管理员在后台创建**：`POST /api/admin/users`。
5. **初始管理员由数据库初始化脚本预置**（`init_data.sql` 写入 1 条 ADMIN 记录），不依赖注册接口，也不依赖"第一个注册的人是管理员"这类隐式规则。
6. 账号创建后状态为启用；管理员可禁用（`PUT /api/admin/users/{id}/status`），禁用后该账号的 Token 立即失效。

**落地动作**
- 修订 API 契约 2.1 节：删除 `CARE`/`ADMIN`，补充错误码与拒绝示例
- 新增 API 契约 9.1 节：`POST /api/admin/users` 创建护工 / 管理员账号
- 数据库初始化脚本预置管理员账号

**受影响文件**：API 接口契约（→v0.2）、`04.编码/数据库/init_data.sql`（待建）

### D-02　家属绑定：必须有授权确认过程，不能"知道手机号就能看"

**问题**
绑定接口只传老人手机号和亲属关系，未定义老人确认或邀请验证。任何人只要知道老人手机号，就能绑定并查看其全部健康数据与 AI 咨询记录。

**证据**
API 契约 v0.1 第 7 章：`POST /api/family/bind`，请求体 `{ "phone": "13800138000", "relation": "儿子" }`。

**决策**

采用**申请 → 确认 → 生效**三段式，绑定关系在未确认前不产生任何数据访问权限。

| 阶段 | 动作 | 关系状态 | 数据权限 |
|---|---|---|---|
| 1. 申请 | 家属提交老人手机号 + 关系 + 备注 | `PENDING` | 无 |
| 2a. 确认 | 老人在本人端确认（或管理员 / 护工线下核验后代确认） | `APPROVED` | 生效 |
| 2b. 拒绝 | 老人或管理员拒绝 | `REJECTED` | 无 |
| 3. 解绑 | 任一方发起，立即失效 | `REVOKED` | 立即收回 |

补充规则：

1. **代确认必须留痕**：管理员或护工代老人确认时，写入 `approved_by`（操作人 ID）与 `approve_note`（原因），供审计。老人本人确认时 `approved_by` 为本人。
2. **解绑是单向即时生效**：任一方解绑即 `REVOKED`，不需要对方同意。解绑后家属立即失去该老人档案、指标、预警、咨询记录的访问权。
3. **历史记录不做物理删除**：`REVOKED` 是状态变更，不是删行，便于追溯"某家属曾有权查看"。
4. **一个老人可绑定多名家属**，上限 5 名，上限值入 `sys_config`（`family_bind_max`），不写死。
5. **同一对家属-老人关系只能有一条 `APPROVED` 或 `PENDING` 记录**，重复申请返回提示，避免刷屏。

**落地动作**
- 重写 API 契约第 7 章：`POST /api/family/bind`（申请）、`GET /api/family/bind-requests`（待我确认的申请）、`PUT /api/family/bind/{id}/confirm`（确认 / 拒绝）、`DELETE`（解绑）
- 老人端新增 1 个界面：UI-ELDER-13 绑定确认（同意 / 拒绝 / 解绑）
- 家属端的申请入口并入已有的 UI-FAMILY-02 绑定老人页，不新增页面
- 界面清单随之由 38 个（核心 29）调整为 39 个（核心 30）〔勘误·2026-09-12：该次计数有误，UI-ELDER-13 已计入老人端 13 个，界面总数实为 38 个（核心 29 + 选配 9），详见《概要设计说明书 v1.0》4.9 节 E-08〕

**受影响文件**：API 接口契约（→v0.2）、界面清单、需求说明书（FR-FAMILY 相关条目补充授权语义）

### D-03　通知范围：只承诺站内通知，不承诺短信与电话

**问题**
需求写"通知紧急联系人"，接口却按页面轮询设计，且系统中只有电话号码字段——有电话号码不等于能送达通知。这属于**承诺与实现不匹配**，答辩时被追问会很难回答。

**证据**
API 契约 v0.1 第 11 章待确认事项第 2 条："预警通知是否需要服务端推送（WebSocket）？当前按前端轮询设计"；需求中"通知紧急联系人"未限定渠道。

**决策**

1. **本期"通知"的明确定义 = 站内通知**：写入 `alert_receiver` 记录，家属端 / 护工端通过未读数轮询拉取并展示红点，打开页面后可见完整预警卡片。
2. **紧急联系人电话的用途仅限"档案信息展示"与"人工联系的依据"**，系统不承诺通过短信或电话送达。需求说明书中涉及短信 / 电话外呼的表述，统一降级为【选配】并注明"需第三方通道与资质，本期不实现"。
3. **轮询周期 30 秒**（未读数接口，数据量极小）；WebSocket 服务端推送列为【选配】，主闭环跑通、时间有余再做。
4. 演示口径（答辩用）：老人录入异常血压 → 家属端 30 秒内红点亮起 → 点开看到预警卡片与 AI 摘要 → 填写处理结果 → 护工端可见处理记录。**全程在系统内完成，不依赖任何外部通道。**

**落地动作**
- 新增 `GET /api/notifications/unread`（未读数，轻量轮询）
- 修订需求说明书中"通知"相关 FR 的措辞，明确渠道
- 界面清单中若有"短信通知配置""电话外呼"条目，改标【选配】

**受影响文件**：API 接口契约（→v0.2）、需求说明书、界面清单

### D-04　AI 摘要失败降级：预警主流程不依赖模型可用性

**问题**
流程把 AI 摘要放在通知之前，未说明模型超时或报错怎么办。一旦模型不可用，预警创建与通知会被整体阻塞——**这正是评审指出的最大风险点**，也是本项目最容易被质疑"AI 只是装饰"的地方。

**证据**
API 契约 v0.1 第 6.1 节预警对象含 `ai_summary`；第 5 章 AI 咨询为同步返回；全文未定义 AI 失败的降级路径。

**决策**

把预警生成拆成**同步主流程**与**异步增强**两段：

```
指标录入
   ↓（同步，必须成功）
规则判定（读 sys_config 阈值，纯代码，不调用模型）
   ↓（同步，必须成功）
写 health_warning：status=PENDING，ai_summary=NULL，summary_status=PENDING
   ↓（同步，必须成功）
按绑定关系写 alert_receiver（家属 / 护工），read_status=UNREAD
   ↓（同步完成，前端已可查到预警）
────────────── 以上是主流程，以下为异步增强 ──────────────
后台任务调用 Risk Agent 生成摘要
   ├ 成功 → 写 ai_summary，summary_status=SUCCESS
   └ 失败 / 超时(>8s) / 重试 1 次仍失败 → summary_status=FAILED
```

配套规则：

1. **`ai_summary` 允许为 NULL**，前端必须处理空值：显示"AI 摘要生成中"或"AI 摘要生成失败，可查看原始数据"，**不得因该字段为空而崩溃或隐藏整条预警**。
2. **高风险（level 3）与紧急（level 4）预警不等待摘要**，标记后立即通知。
3. 提供手动重试入口 `POST /api/alerts/{id}/summary/retry`，由用户或管理员触发。
4. 摘要失败要记入 `ai_log`（【选配】表，若时间不够则用普通日志记录），便于答辩时说明"我们有降级设计且可观测"。
5. **验收标准**：把 `LLM_PROVIDER` 指向一个不可用的地址，完整跑一遍"录入异常 → 预警出现 → 处理 → 记录"。系统除摘要外必须全部正常。这条要作为集成测试用例固定下来。

**落地动作**
- 修订 API 契约第 6 章：预警对象增加 `summary_status`；`ai_summary` 注明可空
- 新增 `POST /api/alerts/{id}/summary/retry`
- 写入集成测试用例（见主闭环追溯表 TC-A-06）

**受影响文件**：API 接口契约（→v0.2）、主闭环追溯表、AI 模块设计

### D-05　已读状态与处理状态分离：一条预警、多个接收人

**问题**
同一条预警可能有多位家属和护工接收，现有设计只有统一的 `VIEWED` 状态。结果是：家属 A 点开看过，家属 B 的界面就显示"已读"；或者护工刚处理完，家属那边却看不到处理进展。

**证据**
API 契约 v0.1 第 6.1 节：`status`：`PENDING` / `VIEWED` / `HANDLED`——把"该预警的处理进度"和"某人看没看过"混在同一个字段里。

**决策**

拆成两个正交的状态，分别落在不同表上：

| 维度 | 归属 | 取值 | 含义 |
|---|---|---|---|
| **处理状态** | `health_warning.status`（预警本身，全局唯一） | `PENDING` → `PROCESSING` → `RESOLVED` / `IGNORED` | 这件事处理到哪一步了 |
| **已读状态** | `alert_receiver.read_status`（每个接收人一条） | `UNREAD` / `READ` | 这个人看没看过 |

规则：

1. 任一家属或护工点开预警详情 → 只更新**自己那条** `alert_receiver.read_status = READ`，不影响其他人。
2. 任一人提交处理结果 → `health_warning.status = RESOLVED`，写 `warning_handle_record`，记录处理人、处理方式、处理说明、处理时间。
3. 处理完成后，其余接收人的界面上该条预警显示为"已由 XXX 于 XX 时间处理"，**未读的人仍需能看到**——已处理不等于已读。
4. 统计口径同步拆分：
   - `pending` = `health_warning.status = PENDING` 的条数（全局）
   - `unread` = 当前用户 `alert_receiver.read_status = UNREAD` 的条数（个人）
5. 增加 `PROCESSING`（处理中）状态，用于"护工已接单但尚未完成"，避免只有"未处理 / 已完成"两态导致中间态无处安放。

**落地动作**
- 修订 API 契约第 6 章：`status` 改为四态；新增 `my_read_status` 字段；6.4 标记已读的作用域明确为"当前用户"
- 数据库表设计：`alert_receiver` 表为本次新增（v0.1 契约未体现）

**受影响文件**：API 接口契约（→v0.2）、数据库 E-R 设计、界面清单（预警详情页、预警列表页）

### D-06　人员安排：按实际投入的 3 人重算，并承认后端是瓶颈

**问题**
企划书按 5 人分工（PM / 后端 / AI Agent / 前端老人端 / 前端家属管理），README 与 OWNERS.md 实际只列 3 人，且后端、数据库、AI Agent、接口层全部集中在 1 人身上。按 5 人排的计划，3 人做不完。

**证据**
`01.需求定义/项目企划书_康养系统_v2.0.md` 第 7 章"团队分工（5 人）"；`README.md` 第 245~290 行只列丘宇乾、梁霁鸣、周彦龙 3 人。

**决策**

1. **分工表按 3 人重写**，"AI Agent"不设独立角色，并入后端负责人（丘宇乾），理由是 Agent 编排与后端接口、数据库强耦合，拆给不同的人会多出大量联调成本。
2. **明确后端是进度瓶颈**，并据此削减范围：以下【选配】项默认**不做**，只有当主闭环跑通且距 10/16 还有余量时才启动：
   - 语音输入 STT / 语音播报 TTS
   - 知识库文档上传与自动解析建索引（FR-KB-005）
   - 数据导出 Excel / PDF
   - 统计大屏
   - AI 流式输出 SSE
   - WebSocket 服务端推送
   - 短信 / 电话外呼
3. **前端 2 人的排期按"主闭环优先"重排**：29 个核心界面中，先做主闭环必需的 8 个（见第 4 节），其余按优先级顺延，不追求"所有页面同时开工"。
4. 测试（周彦龙）不与编码并行等待，而是**阶段性介入**：主闭环完成后立即做第一轮黑盒，不要等到第 8 周。

**落地动作**
- 修订企划书第 7 章为 3 人分工表
- 修订 AGENTS.md / CLAUDE.md 中的"5 人小组"表述
- 主闭环追溯表作为 3 人共同的验收基准

**受影响文件**：企划书、AGENTS.md、CLAUDE.md、README.md

## 3. AI 模块的责任边界

评审意见："多 Agent 的成果应体现在'不同问题走不同的数据和处理路径'，而不只是界面显示几个 Agent 名称。"本節把这句话落成可执行的规定。

### R-01　业务代码负责一切确定性操作

以下逻辑**必须由 Python 代码实现，不交给模型**：

- 权限校验：当前用户能否查看某个老人档案（依据 `family_bind` / `care_relation` 表）
- 指标统计：均值、最值、趋势斜率、近 N 天序列
- 阈值判断：读 `sys_config` 后与实测值比对，判定 level 0~3
- 预警写入：写 `health_warning` 与 `alert_receiver`
- 状态流转：PENDING → PROCESSING → RESOLVED / IGNORED
- 安全分级兜底：即使模型判定为 L1，命中紧急关键词（胸痛、呼吸困难、意识丧失、跌倒无法起身等）仍由代码强制升级为 L4

### R-02　AI 只负责语言理解与解释

- 意图识别：把用户问题路由到 NORMAL / DATA / ABNORMAL / EMERGENCY
- 知识检索后的回答组织：基于 RAG 检索结果生成自然语言回答，附来源标注
- 历史趋势说明：把结构化数据解释成人能看懂的话
- 预警摘要：把一条预警的上下文压缩成一两段说明

### R-03　编排层负责连接与失败处理

- 规定每个分支**能调用哪些工具**（工具白名单，不是让模型自由发挥）
- 规定每个分支**返回哪些字段**（契约固定，前端按字段渲染）
- 规定**超时与失败后怎么处理**（见 D-04 降级策略）
- 记录 `intent`、`agent`、`safety_level`、`sources`，用于前端展示与答辩举证

### R-04　禁止事项（违反即打回）

1. **禁止让模型生成并执行任意 SQL**——只能用预定义的查询函数，参数由代码校验
2. **禁止让模型判断用户是否有权查看某位老人**——权限是代码的事
3. **禁止让模型直接写数据库**——模型只产出文本，写入由代码完成
4. **禁止把模型输出当作阈值或诊断结论**——阈值来自 `sys_config`，回答必须带免责声明
5. **禁止在预警主流程中同步等待模型**（见 D-04）

### R-05　多 Agent 的验收标准

判断"多 Agent 是否真的落地"，看的是**数据路径不同**，不是界面上有没有 Agent 名称：

| 意图 | 执行 Agent | 必须走的数据路径 | 不通过的判据 |
|---|---|---|---|
| NORMAL（日常咨询） | Health Agent | 知识库 RAG 检索 | 若它去查了老人历史指标，说明路由错了 |
| DATA（询问我的数据） | HealthData Agent | 必查该老人历史指标 | 若回答里没有任何真实数值，说明没接数据 |
| ABNORMAL（异常 / 预警相关） | Risk Agent | 必查预警记录 + 指标趋势 | 若回答不引用具体预警，说明没走这条路 |
| EMERGENCY（紧急症状） | Emergency Agent | 强制写预警 + 立即通知 + 引导就医 | 若只是文字劝告而未落预警，说明没实现 |

这四条会写进集成测试用例（见主闭环追溯表 TC-B 系列）。

## 4. 范围收敛：先证明一个闭环跑得通

评审意见："最值得投入的工作，是统一需求和接口、尽早证明闭环跑得通。"

### 4.1 最小闭环（MVP）定义

**一个老人、一个家属、一类指标（血压）**，跑完下面这条链：

```
老人录入血压 178/102
  → 规则判定为 level 3（高风险）
  → 生成预警（主流程，不依赖 AI）
  → 异步补 AI 摘要
  → 家属端 30 秒内出现未读红点与预警卡片
  → 家属填写处理结果（已电话联系，安排复诊）
  → 预警转为 RESOLVED，写入处理记录
  → 护工端可查到该处理记录
```

这条链能跑通，答辩就有了最核心的证据：**无须老人主动提问，异常数据自动变成家属待办，且处理过程有记录可查。**

第二条链（AI 咨询）在 MVP 中简化为：老人或家属提问 → 意图路由 → 查知识库或查历史指标 → 带来源的回答 + 免责声明。

### 4.2 MVP 必需的 8 个界面（前端优先做这 8 个）

| 序 | 界面 | 归属 | 说明 |
|---|---|---|---|
| 1 | 登录 / 注册 | 公共 | 注册角色白名单（D-01） |
| 2 | 老人端首页 | 梁霁鸣 | 已有原型 P1 |
| 3 | 指标录入 | 梁霁鸣 | 录入即触发判定 |
| 4 | AI 健康咨询 | 梁霁鸣 | 已有原型 P2 |
| 5 | 预警列表 / 通知中心 | 梁霁鸣 | 已有原型 P3，需按 D-05 显示"我的已读" |
| 6 | 预警详情 + 处理 | 梁霁鸣 | 需按 D-04 处理 ai_summary 为空 |
| 7 | 家属绑定申请 / 确认 | 梁霁鸣 | **本次新增**（D-02） |
| 8 | 护工端老人列表 + 处理记录 | 周彦龙 | 已有原型 P4 |

管理员端（预警规则配置、知识库、统计）在 MVP 中可用最简版本：只要能把阈值改对即可（已有原型 P5）。
