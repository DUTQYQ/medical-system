## 三、关键技术结论（可被验证的论断）

### 3.1 架构

- 本项目为 **B/S 应用（Web）项目**，非嵌入式项目；架构采用前后端分离 + 分层设计，共 7 层：
  用户层 → 表示层（Vue3）→ 接口层（FastAPI）→ 应用服务层 → AI Agent 层（LangGraph）→ 数据访问层（SQLAlchemy 2.0）→ 数据存储层（MySQL 8 + 向量库）
- AI Agent 编排：意图识别路由到 4 个业务 Agent（Health / HealthData / Risk / Emergency）+ Alert 守护 Agent
- **AI 摘要为异步增强，预警主流程不同步等待模型**（依据《设计决策记录》D-04），超时阈值 8 秒
- 大模型可换：切换只需改 `.env` 的 `LLM_PROVIDER`，不改代码

### 3.2 数据库

- 共 **15 张表 = 核心 11 + 选配 4**
- 核心表：`user`、`elder_profile`、`family_bind`、`care_relation`、`health_record`、`health_warning`、`alert_receiver`、`warning_handle_record`、`chat_session`、`chat_message`、`sys_config`
- 选配表：`medication`、`knowledge_document`、`knowledge_chunk`、`ai_log`
- 四项核心设计决策：
  1. **配置入表**：阈值、上限等一律存 `sys_config`，代码不得硬编码
  2. **统一指标表**：5 类指标共用 `health_record`，以 `type` 区分
  3. **处理状态与已读状态正交**：`health_warning.status`（全局）与 `alert_receiver.read_status`（每人）分离（依据 D-05）
  4. **AI 摘要允许为空**：`ai_summary` 可为 NULL，`summary_status` 记录生成状态（依据 D-04）
- 外键统一在建表后用 `ALTER TABLE` 补充，避免建表依赖顺序

### 3.3 E-R 识别方法（七步法）

1. 收集用例规约 → 2. 提取名词为候选实体 → 3. 提取动词为候选联系 → 4. 过滤归一（去同义词/行为词/外部系统/纯属性）→ 5. 确定属性与主键 → 6. 确定联系类型与基数 → 7. M:N 拆关联实体 + 规范化 + 出图

**实例结论**："家属绑定老人"用例中，"绑定"是 M:N 联系且带生命周期（PENDING/APPROVED/REJECTED/REVOKED），因此必须建为独立实体 `family_bind`，而不能把 `family_id` 塞进 `elder_profile`。

### 3.4 数据库工具选型

- **推荐组合**：MySQL Workbench（权威建模 + 正向工程生成 DDL）+ drawDB 或 dbdiagram.io（评审出图）
- **明确不推荐**：PowerDesigner、ER/Studio（功能过剩且商用收费）
